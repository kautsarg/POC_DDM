# RC-POC (03e): Does Concentration Help Classification, or Vice Versa?

## Research Question

Compare four training strategies on the CGD (CNN+GRU Dual) backbone.
The primary target is to improve **classification**; regression (concentration) is the auxiliary signal.

| Model | Role | Hypothesis |
|---|---|---|
| `cgd_rc_poc` | Pure cls baseline | No concentration supervision at all |
| `mtl_cgd_rc_poc` | Joint cls+reg | Does joint reg supervision improve cls? |
| `gru_rcfd_cgd_rc_poc` | RCFD: reg→FiLM→cls | Does knowing concentration help classify? |
| `gru_ccfd_cgd_rc_poc` | CCFD-POC: frozen-cls→FiLM→reg | Reverse: does a frozen classifier help predict concentration? |

The key novelty of model 1.d vs 03d CCFD: the classification backbone in 1.d is **frozen/pre-trained** (model 1.a),
not trained jointly. This cleanly isolates whether a converged classifier's signal helps regression.

## Models (16 total = 4 types × 4 SC levels)

### Model 1.a — `cgd_rc_poc` (CNN+GRU Dual, pure classification)

Pure classification baseline — no regression head at all.
```
Input → _build_cnn_gru_dual_branches_mtl(inputs)
      → z_emb
      → cls_head → cls_out  (only output)
```
Builder: adapt from non-MTL `cnn_gru_dual` pattern in `model_utils_mtl.py` / `config.py`.  
SC variants add `_proj_head(z_emb)` (SC1), CNN+GRU branch heads (SC2), both (SC3).

Keys: `cgd_rc_poc`, `cgd_rc_poc_sc1`, `cgd_rc_poc_sc2`, `cgd_rc_poc_sc3`

---

### Model 1.b — `mtl_cgd_rc_poc` (CNN+GRU Dual MTL, joint cls+reg)

Same backbone as 1.a but adds a regression head. Same as `cnn_gru_dual_mtl` in `model_utils_mtl.py`.
```
Input → _build_cnn_gru_dual_branches_mtl(inputs)
      → z_emb
      → cls_head → cls_out  (position 0)
      → reg_head → reg_out  (position 1)
```
Builder: `create_cnn_gru_dual_mtl_model` from `model_utils_mtl.py`.  
SC variants: `create_cnn_gru_dual_supcon_mtl_model` etc. from `model_utils_supcon.py`.

Keys: `mtl_cgd_rc_poc`, `mtl_cgd_rc_poc_sc1`, `mtl_cgd_rc_poc_sc2`, `mtl_cgd_rc_poc_sc3`

---

### Model 1.c — `gru_rcfd_cgd_rc_poc` (RCFD, same as `model_utils_rcfd.py`)

Exact same architecture as `gru_rcfd_cgd`. GRU early encoder predicts concentration,
which FiLM-conditions the CGD classification backbone.
```
Input → GRU early encoder (BiGRU-16 → Dense32 → Dense16 → Dense8 → early_reg)
      → stop_gradient(early_reg)
      → CGD backbone → z_raw → FiLM(early_reg) → Dropout → z_cond
      → cls_head → cls_out  (position 0, primary)
      → reg_head → reg_out  (position 1, auxiliary / from z_cond)
```
Builder: `create_gru_rcfd_cgd_model` / supcon variants from `model_utils_rcfd.py`.

Keys: `gru_rcfd_cgd_rc_poc`, `gru_rcfd_cgd_rc_poc_sc1`, `gru_rcfd_cgd_rc_poc_sc2`, `gru_rcfd_cgd_rc_poc_sc3`

---

### Model 1.d — `gru_ccfd_cgd_rc_poc` (NEW: Frozen-backbone CCFD)

Reverse of 1.c: a **frozen, pre-trained classifier (1.a)** conditions a CGD regression backbone via FiLM.
```
Input → [FROZEN] cgd_rc_poc_sc{n} (loaded from .keras, trainable=False)
          └─ cls_probs (softmax, n_classes) ──────────────┐
                                                          ↓ (stop_gradient already implicit via frozen)
Input → _build_cnn_gru_dual_branches_mtl(inputs) → z_raw → FiLM(cls_probs, name_prefix='cfilm_poc')
      → Dropout → z_cond
      → reg_head → reg_out  (only trainable output, primary task)
```

- Frozen backbone: `{rc_poc_dir}/models/cgd_rc_poc_sc{n}_{filter}_{curve_type}_{n_splits}fold_model.keras`
  — **same SC level** as the variant being trained (`sc1` loads `cgd_rc_poc_sc1`, etc.)
- `base_model.trainable = False`
- FiLM: `_apply_film_scalar(cls_probs, z_raw, emb_dim=96, name_prefix='cfilm_poc')`
  — works with n_classes-dim input (BN + Dense projections handle non-scalar conditioning)
- FiLM architecture is the same as in 1.c (same `_apply_film_scalar` implementation)
- **cls loss weight = 0**: reg_out is the sole trainable objective; cls_probs is not an output of the model  
  (unlike other models, model 1.d outputs only `[reg_out]` — no cls output at position 0)
- SC variants add SupCon on the **trainable** CGD regression backbone only (not frozen backbone):
  - SC1 → `_proj_head(z_cond, 'fused')`
  - SC2 → `_proj_head(cnn_emb, 'cnn')` + `_proj_head(gru_emb, 'seq')`
  - SC3 → SC2 + `_proj_head(z_cond, 'fused')`

Keys: `gru_ccfd_cgd_rc_poc`, `gru_ccfd_cgd_rc_poc_sc1`, `gru_ccfd_cgd_rc_poc_sc2`, `gru_ccfd_cgd_rc_poc_sc3`

## Note on SC and Regression

> **Q (3.2):** "In CNN+GRU Dual and RCFD, does SC only affect classification? Not the regression backbone?"

**Partially correct. Nuance:**

- **Model 1.a** (pure cls): SC acts on `z_emb`. No regression — SC purely shapes classification.
- **Model 1.b** (MTL): `z_emb` feeds **both** cls_head and reg_head. SC reshapes `z_emb` using CLASS labels,
  which biases the backbone toward class-discriminative representations. Regression is trained via MSE
  on the same `z_emb` — so SC indirectly affects the regression backbone too, though the intent is classification.
- **Model 1.c** (RCFD): SC acts on the **CGD main backbone** (`z_cond`, CNN branch, GRU branch).
  The `reg_out` in RCFD comes from `z_cond` (main backbone) and is also somewhat shaped by SC.
  The **GRU early encoder** (which produces `early_reg` for FiLM conditioning) is **NOT** touched by SC —
  this is the regression-dedicated lightweight encoder, and it remains purely MSE-supervised.
- **Model 1.d** (CCFD-POC): SC acts on the **trainable CGD regression backbone** using class labels.
  The frozen cls backbone is fixed. SC here shapes the regression backbone to be class-discriminative —
  analogous to how RCFD SC shapes the main backbone.

**Result keys per model** (5 each, 80 total):
```
y_preds_AC_{key}_         # cls predictions   (N/A for 1.d → store REG_SENTINEL or skip)
y_probs_AC_{key}_         # cls probabilities  (N/A for 1.d)
classes_AC_{key}_         # encoder classes    (N/A for 1.d)
y_reg_preds_{key}_        # regression predictions
y_reg_trues_{key}_        # regression ground truths
```
For model 1.a (cls only): no `y_reg_preds_` / `y_reg_trues_` keys.  
For model 1.d (reg only): no `y_preds_AC_` / `y_probs_AC_` / `classes_AC_` keys.

- n_splits>1 → `{exp_folder}/rc_poc/rc_poc_results_5fold.joblib`

## Training Order (serial dependency)

Model 1.d requires saved `.keras` of model 1.a. Training order must be:

```
Pass 1: train 1.a, 1.b, 1.c (all 12 models across SC0-3) — save 1.a keras at fold 0
Pass 2: train 1.d (all 4 SC levels) — loads cgd_rc_poc_sc{n} keras from pass 1
```

The script handles this with two sequential loops. If 1.a keras not found, raise a clear error
rather than silently training wrong.

## Design Decisions (resolved)

| # | Decision | Choice |
|---|---|---|
| 3.1 | Cls loss in model 1.d | **Omit cls output entirely**. 1.d outputs `[reg_out]` only; no cls supervision |
| 3.2 | SC coupling for 1.d frozen backbone | **Corresponding SC level** (`sc1` loads `cgd_rc_poc_sc1`) |
| 3.3 | `_apply_film_scalar` with n_classes-dim | **Use as-is** (`name_prefix='cfilm_poc'`) — BN + Dense handle vector input |
| 3.4 | Outlier filter support | **`[None]` only** for now |
| 3.5 | Leaderboard | **Only the 16 rc_poc models** from this script |
| 3.6 | `--supcon` arg | **Not needed** — all SC levels run in one invocation |
| 3.7 | Keras class registration | **New packages** (`rc_poc_cls`, `rc_poc_mtl`, `rc_poc_rcfd`, `rc_poc_ccfd`) |
