# Arch-PoC (03f): Dual vs Serial vs Mixed CNN+GRU

## Research Question

All current top models use a **parallel dual branch** (CNN ‖ GRU → concat → dense).
The question is whether routing CNN features *through* the GRU (serial) is better,
and whether combining both ideas (CNN ‖ CNN→GRU dual) outperforms either alone.

| Model key | Architecture | Hypothesis |
|---|---|---|
| `cgd_arch_poc` | CNN+GRU Dual (existing) | Baseline — parallel branches, each sees raw signal |
| `cgs_arch_poc` | CNN+GRU Serial (new) | CNN pre-processes signal; GRU models temporal patterns over CNN features |
| `ccgd_arch_poc` | CNN + (CNN→GRU) Dual (new) | Direct CNN summary + serial CNN→GRU branch — best of both? |

Three comparisons:
1. **CGS vs CGD**: does serial CNN→GRU beat parallel?
2. **CCGD vs CGS**: does a direct CNN bypass recover info the serial GRU may compress away?
3. **CCGD vs CGD**: is the new dual (CNN ‖ CNN→GRU) better than old dual (CNN ‖ GRU)?

## Architectures

### Model A — `cgd_arch_poc` (CNN+GRU Dual, existing)

**Reuse `_build_cnn_gru_dual_branches_mtl` unchanged.**

```
Input (T, 1)
  ├─ CNN branch → Conv1D(16,5) → Conv1D(8,3) → Flatten → Dense(32) = cnn_emb (32)
  └─ GRU branch → BiGRU(32,seq) → LN → BiGRU(16) → Drop(0.2) → Dense(64) = gru_emb (64)
  → Concat([cnn_emb, gru_emb]) → Dense(96, relu) → Drop(0.2) → z (96-dim)
```

SC branches: `cnn_emb` (32) and `gru_emb` (64) — same as existing `cnn_gru_dual` SC2/SC3.

---

### Model B — `cgs_arch_poc` (CNN+GRU Serial, new)

**New builder: `_build_cnn_gru_serial_branches`.**

```
Input (T, 1)
  → Conv1D(16, 5, relu)                        #  (T-4, 16)
  → Conv1D(8,  3, relu)                        #  (T-6,  8) = cnn_seq  [serial feed to GRU]
  → BiGRU(32, return_sequences=True)           #  (T-6, 64)
  → LayerNormalization
  → BiGRU(16)                                  #  (32,)     = gru_raw
  → Dropout(0.2)
  → Dense(64, relu) → Dropout(0.2)             #  z (64-dim)
```

SC2 taps — side branches that do NOT affect z, only used for contrastive projections:
- `cnn_tap`: `GlobalAveragePooling1D(cnn_seq) → Dense(32, relu)` — pooled CNN feature summary (32-dim)
- `gru_tap`: `gru_raw` directly (32-dim, before Dense(64))

SC assignments:
- SC0: z only
- SC1: proj on z
- SC2: proj on cnn_tap + gru_tap
- SC3: SC2 + SC1

---

### Model C — `ccgd_arch_poc` (CNN + CNN→GRU Dual, new)

**New builder: `_build_cnn_cnngru_dual_branches`.**

Two independent parallel branches (separate CNN weights each):

```
Input (T, 1)
  ├─ Branch A (CNN only)
  │    → Conv1D(16,5,relu) → Conv1D(8,3,relu) → Flatten → Dense(32,relu)  = cnn_emb (32)
  │
  └─ Branch B (CNN→GRU serial)
       → Conv1D(16,5,relu) → Conv1D(8,3,relu)            # (T-6, 8) sequence
       → BiGRU(32,seq) → LN → BiGRU(16) → Drop(0.2)     # gru_raw (32)
       → Dense(64, relu)                                  = cnngru_emb (64)

  → Concat([cnn_emb, cnngru_emb]) → Dense(96, relu) → Drop(0.2) → z (96-dim)
```

SC branches: `cnn_emb` (32) and `cnngru_emb` (64) — same pattern as CGD SC2/SC3.

## Design Decisions (open)

| # | Question | Proposed |
|---|---|---|
| D1 | Should CGS SC2 taps (cnn_tap, gru_tap) be included in the forward pass or only in SC2/SC3 variants? | **Side-tap only in SC2/SC3 variants** — `return_branches` controls exposure; SC0/SC1 do not build the tap Dense layer |
| D2 | Should Branch A and Branch B in CCGD share CNN weights? | **No** — separate CNN weights per branch to allow each to specialise |
| D3 | Outlier filters? | **`[None]` only** for now (same as 03e) |
| D4 | Leaderboard | **Only 12 arch_poc models** from this script |
| D5 | SupCon temperature | **Same `SUPCON_TEMP` constant** from model_utils_supcon.py |
